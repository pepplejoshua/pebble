# Amendment: delayed `HasComponent` constraint for tuple member access

**Status:** Accepted and implemented. Tuple member access (`pair.0`) is fully
working and verified (see `14-v2-v1-checker-backend-parity-audit.md`'s "Tuple
member `.0`, `.1`, and so on" row). Kept here as the design record and
rationale for the `HasComponent` constraint; the normative text lives in
`06a`/`06b` per the notes below.

**Problem:** tuple member access (`pair.0`) cannot be expressed with the accepted
`05b` constraint set. Phase 6 has no fact to emit, so the member result term is
never constrained and leaks an unresolved variable into every enclosing
expression.

## Evidence

On `main` at `83cb4ea`:

```pebble
fn f() void {
    let pair (i32, str) = (1, "a");
    let first i32 = pair.0;
}
```

fails to solve with `T0510 "inference variable has no unique semantic type"`,
origin role `binding initializer`. The receiver is fully annotated, so this is
not an ordering or evidence problem — no constraint relating the member result
to component 0 exists at all.

The closed constraint set in `05b` §"Constraints and provenance" contains no
ordinal relation:

- `HasField(receiverType, name, fieldType)` matches by **name**. A tuple
  component has an ordinal, not a spelling, and `05a` tuple structure exposes no
  synthetic field names to borrow.
- `Indexable`/`Sliceable` are the existing delayed structural relations, and
  both deliberately exclude tuples. `06b` §"Indexing and slicing" states
  "Pointers and tuples are not indexable"; reusing `Indexable` would contradict
  that and would also lose the ordinal, which must be known statically.

`06a` §"Members, calls, and generic applications" currently says only:

> Tuple numeric members retain the parsed index and base; structural
> decomposition belongs to their generation shape and final legality to `06b`.

"belongs to their generation shape" has no operational meaning here: the
member's own shape is exactly what is unknown, and the receiver's `Shape` fact
relates the receiver to its components, never the member occurrence to one of
them. This sentence is the specification gap.

## Rejected alternative

Decomposing tuples inside `06a` whenever the receiver type happens to be known
at the time the member is visited. Rejected: it only works when the receiver
resolves before the member occurrence is reached, so a tuple returned from a
call, produced by a generic instantiation, or bound later in the same expression
would still fail. That is exactly the traversal-order dependence `06a` forbids
("The constraint delays when the base is unresolved and never guesses from
traversal order"), and it would have to be redone as a delayed constraint later.

## Amendment to `05b-algebraic-inference.md`

### 1. Constraint list (§"Constraints and provenance")

Add one line to the closed tagged set, immediately after `HasField`:

```text
HasComponent(receiverType, ordinal, resultType)
```

### 2. Constructor surface (same section)

Add one constructor, immediately after `HasField`:

```go
func HasComponent(receiver Term, ordinal uint32, result Term, origin Origin) Constraint
```

`ordinal` is zero-based and copied by value. As with every other constructor,
it rejects invalid terms when added to a session and retains no caller-owned
storage.

### 3. Solver table row

Insert after the `HasField` row:

| Constraint | Generated by | Progress, delay, success, and failure | Policy owner |
| --- | --- | --- | --- |
| `HasComponent(recv,ordinal,result)` | authored tuple component access | Strip no conversions. Delay until the receiver is a known tuple type or a tuple shape whose arity is fixed. On a tuple of arity `N`, an `ordinal` less than `N` equates `result` with that component and succeeds. An `ordinal` of `N` or greater fails `T0507`. A known nontuple receiver fails `T0507`; unresolved structure uses ordinary `T0510`. A rigid type parameter makes the constraint checker-deferred complete, recovers `result` to `Error` without an inference diagnostic, and invents no trait; phase 6 retains the unsupported checker requirement. `Error` suppresses it. | `05b` closed component structure; phase 6 owns place, mutability, and legality |

Note the arity condition: a tuple **shape** with unresolved leaves may still
have fixed arity, and that is enough to select and equate the component. Only an
unresolved *constructor* forces a delay. This keeps the constraint monotonic and
lets `pair.0` resolve before the other components do.

### 4. Shared delayed-constraint paragraph

The paragraph beginning "`Callable`, `Indexable`, and `Sliceable` participate in
the same single solve" must include the new constraint. Replace that opening
with:

> `Callable`, `Indexable`, `Sliceable`, and `HasComponent` participate in the
> same single solve

The rest of the paragraph is unchanged and applies verbatim: same ascending
`ConstraintID` worklists, charged to the existing requeue/decomposition limits,
no private retry loop or unbounded watcher, exact origins retained, wakes only
from monotonic root/shape progress, equation-insertion-order independent,
silently complete through `Error`, and exposing no phase-6 legality policy.

### 5. Slice `05b.5`

In the sentence listing what that slice implements, change

> delayed member/callable/indexable/sliceable constraints

to

> delayed member/component/callable/indexable/sliceable constraints

No other slice changes. `05b.6` needs no change: the constructor is added
alongside the existing ones and is covered by its current "constraint
constructors" ownership.

### 6. Testing contract

Add to the required `05b` coverage:

- a tuple component resolved from a fully known receiver;
- a tuple component resolved from a tuple **shape** with fixed arity and one
  still-unresolved sibling leaf, proving the constraint does not wait for
  unrelated components;
- the same case with the constraint added **before** the receiver's shape,
  proving equation-insertion-order independence;
- an out-of-range ordinal failing `T0507`;
- a known nontuple receiver failing `T0507`;
- a rigid type parameter recovering `result` to `Error` with no inference
  diagnostic;
- an `Error` receiver suppressing the constraint.

## Dependent change in `06a-semantic-fact-generation.md`

One sentence in §"Members, calls, and generic applications". Replace:

> Tuple numeric members retain the parsed index and base; structural
> decomposition belongs to their generation shape and final legality to `06b`.

with:

> A tuple numeric member visits the receiver, allocates and publishes the member
> result, emits `HasComponent(receiver,ordinal,result)`, and retains the parsed
> index, base, and place projection. Final legality belongs to `06b`.

This matches the existing type-directed field rule one paragraph above, which
already emits `HasField` and retains a place projection.

## Dependent note in `06b-validation-and-typed-ir.md`

No contract change. `06b` already consumes `memberTuple` through
`memberRecord`/`placeProjection` and already owns tuple place and legality
policy. The existing statement that tuples are not indexable is unaffected —
`HasComponent` is a distinct relation with a static ordinal, not indexing.

## Non-goals

Out of scope for this amendment, and must not be added opportunistically:

- automatic dereference of a pointer-to-tuple receiver — `HasComponent` mirrors
  `HasField` and requires another rule to make pointer/optional behavior
  explicit first;
- runtime or computed component indices — the ordinal is a parse-time constant;
- tuple indexing through `Indexable`, which stays excluded;
- any generic requirement kind for tuple access on a rigid parameter. The
  checker-deferred recovery path above is the accepted behavior, exactly as for
  `Callable`/`Indexable`/`Sliceable`.

## Acceptance

After the `05b` change and the dependent `06a` change, this must solve cleanly:

```pebble
fn f() void {
    let pair (i32, str) = (1, "a");
    let first i32 = pair.0;
    let second str = pair.1;
}
```

and an out-of-range `pair.2` must produce exactly one `T0507`.

## Sequencing

`05b.5` is already implemented and accepted, so this reopens a completed slice.
It is additive: no existing constraint, solver stage, or public signature
changes, and no accepted fixture depends on the current failing behavior. The
dependent `06a` change touches `member_facts.go` only and must not land before
the `05b` constructor exists.
