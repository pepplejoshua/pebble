# Prole Design Notes

Prole is Pebble's VM/runtime library. It is intentionally separate from `pebc`.
The compiler should use Prole the same way it uses Pastel: as an independent C
library with its own public API.

## Direction

Pebble keeps the C backend as the native systems target. Prole becomes the VM
target for fast iteration, bytecode inspection, REPL support, comptime
execution, scripting, and eventually actor-style runtime features.

The first compiler integration should branch after normal parsing, import
resolution, type checking, and entry-point verification. Prole bytecode
generation should consume checked AST nodes with `resolved_type` populated. It
should not become a second parser or second type checker.

## Library Boundary

`prole/` should not depend on Pebble ASTs, compiler options, checker state,
module tables, or arena allocators. It may use Pastel for colored output.

The Pebble compiler adapter should live outside Prole:

```text
src/prole_gen.h
src/prole_gen.c
```

That adapter translates checked Pebble AST into Prole bytecode.

## Layout

Current and expected shape:

```text
prole/

```

## Bytecode Module

Prole should have a bytecode module concept, but it is a loadable bytecode unit,
not a direct clone of Pebble source modules.

Reasons:

- Store compiled functions, native references, entry point, and lookup tables.
- Leave room for future bytecode linking/imports.
- Support REPL accumulation through a synthetic module like `__repl`.
- Give the disassembler and assembler a clear top-level structure.
- Give runtime/native bindings a stable place to live.

The first compiler backend can flatten checked Pebble modules into one Prole
module.

## Bytecode Style

Use a register VM.

Initial value types:

```text
void
i64
bool
```

Initial opcode family:

```text
nop
const.i64
const.bool
load.local
store.local
add.i64
sub.i64
mul.i64
div.i64
mod.i64
eq.i64
ne.i64
lt.i64
le.i64
gt.i64
ge.i64
jump
jif
call
call.native
print
ret
ret.void
```

Use dotted opcode names in assembler/disassembler output. They are readable,
easy to type, and scale naturally to future types.

Call instructions use contiguous argument registers:

```text
call r10, fn1, r4, 2
```

This means:

```text
r10 = destination register for the return value
fn1 = function index/name
r4  = first argument register
2   = argument count
```

The VM reads arguments from neighboring registers:

```text
arg0 = r4
arg1 = r5
```

So bytecode generation must arrange call arguments into contiguous registers
before emitting `call` or `call.native`.

## Assembler And Disassembler

Implement the disassembler before the assembler. Compiler-generated bytecode
needs to be inspectable immediately.

The disassembler should emit syntax that is pleasant to write by hand and close
to what the assembler accepts later.

Example:

```text
module smoke
entry main

fn main/0 -> void
  const.i64 r0, 42
  print r0
  ret.void
```

Expected future label syntax:

```text
fn loop/0 -> void
.start:
  jump .start
```

Labels are first-class in assembly but compiled away into instruction offsets.
The disassembler should eventually regenerate readable labels by default.

Assembler quality should follow the lessons from `parser2`:

- Lexer owns source spans.
- Diagnostics accumulate instead of bailing at the first error.
- Recovery should synchronize around clear anchors such as labels, functions,
  newlines, and module directives.
- No fixed caps for functions, labels, params, locals, or instructions.
- Invalid assembler files should be tested from day one.
- Disassembler output should eventually round-trip through the assembler.

## Diagnostics

Prole duplicates the SourceSpan-style design under `ProleSpan`. Diagnostics
currently use `malloc/free` so the library is independent from `pebc`'s arena
allocator.

This is acceptable for early diagnostics. Later, diagnostics can accept a
`ProleAllocator` if allocation control becomes important.

## Allocators

The VM should support allocator hooks from day one of runtime implementation.
Production VMs usually separate allocation by lifetime and purpose:

```text
bytecode/module metadata
VM instance state
call frames and execution stacks
runtime heap objects
temporary compiler/emitter scratch
debug metadata
```

Start with a small allocator interface:

```c
typedef struct ProleAllocator {
  void *ctx;
  void *(*alloc)(void *ctx, size_t size);
  void *(*realloc)(void *ctx, void *ptr, size_t old_size, size_t new_size);
  void (*free)(void *ctx, void *ptr, size_t size);
} ProleAllocator;
```

Public constructors should accept an allocator and fall back to malloc when
`NULL` is passed:

```c
ProleModule *prole_module_new(const char *name, ProleAllocator *allocator);
ProleVm *prole_vm_new(ProleAllocator *allocator);
```

Allocator hooks now exist for bytecode/module ownership. Keep extending this
before the VM starts owning significant runtime state.

## Debugging

Prole should support debugging from the first VM implementation. The VM should
be step-able; `run()` should be a loop over `step()`.

Expected API shape:

```c
typedef enum {
  PROLE_STEP_OK,
  PROLE_STEP_RETURNED,
  PROLE_STEP_BREAKPOINT,
  PROLE_STEP_TRAP,
} ProleStepResult;

ProleStepResult prole_vm_step(ProleVm *vm);
bool prole_vm_run(ProleVm *vm);
```

Expose read-only inspection helpers:

```c
const ProleFrame *prole_vm_current_frame(const ProleVm *vm);
const ProleFunction *prole_vm_current_function(const ProleVm *vm);
size_t prole_vm_ip(const ProleVm *vm);
ProleValue prole_vm_read_register(const ProleVm *vm, uint32_t reg);
```

Bytecode should eventually carry optional debug metadata:

```text
instruction offset -> source span
function index -> source function name/module
local/register index -> optional display name
```

The debugger API should not assume a UI. A future UI should be one client of the
same VM/debug API used by tests and command-line tools.

## Milestones

1. Keep Prole separate from `pebc`.
2. Build bytecode containers and plain disassembly.
3. Add allocator hooks before implementing VM runtime state.
4. Add a step-able VM for constants, print, and return.
5. Add arithmetic, locals, and direct calls.
6. Add `if`/`while` through jumps and labels.
7. Wire `pebc --target=prole --dump-bc` after type checking.
8. Add assembler after the disassembler format stabilizes.
9. Add REPL.
10. Use the VM for limited comptime execution.
11. Add heap objects.
12. Add native runtime bridge.
13. Explore tasks, mailboxes, receive, and supervision.

## Current Status

Initial scaffold exists:

- Public umbrella header.
- Prole span type.
- Prole diagnostics using malloc/free and Pastel formatting.
- Prole allocator hooks with malloc-backed and arena-backed allocators.
- Bytecode module/function/native/instruction containers.
- Plain disassembler.
- `make prole-smoke` target.
